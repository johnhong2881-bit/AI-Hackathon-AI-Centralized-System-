## 3. 业务逻辑

### 3.1 数据模型

```
Project   { id, name, description, deadline(带时区), timezone, rubric_text?, assignment_text }
Member    { id, project_id, name, is_leader, strengths:[{skill, level}], weaknesses:[skill],
            availability: 周一到周日各 {on, hours} }
Task      { id, project_id, title, description, priority(H/M/L), priority_reason,
            depends_on:[task_id], required_skills:[skill], locked, overridden_done,
            assignments:[Assignment] }
Assignment{ member_id, allocated_hours, remaining_hours,
            status(todo/in_progress/done), accept(pending/accepted/rejected), reject_reason? }
ChangeLog { time, actor(AI/Leader/Member), what, before, after }   // 即使没有 Activity 页,也建议保存
```

### 3.2 表单验证

**Create**
- 名称:非空,最多 100 字。
- 成员人数:整数 2–10。
- 作业:有 PDF(≤20 MB,类型为 PDF)或有贴上的文字,至少一项。
- Deadline:日期时间必须晚于"现在"(用项目时区比较)。
- Rubric:可为空;为空时告知用户 AI 会尝试从作业中寻找。

**Team**
- 名字非空,不能重复(忽略大小写与前后空白)。
- 强项至少 1 项,每项有等级。弱项至少 1 项。
- 同一技能不能同时在强项与弱项。
- 每天小时数在 0–24;一周总和 > 0。
- 成员数应等于第一页设定的人数,不等时提醒但不阻止,不要自动更改。

### 3.3 容量与排程(核心)

**可用小时**:成员某一天的容量 = 当天开关为开 ? 小时数 : 0。"今天"是第 0 天,星期几决定用哪一天的设定。

**一个成员的剩余工作** = 他在所有未完成、未被拒绝的分配里的剩余小时之和。

**排程算法**(逐日、按优先级、尊重依赖):

```
1. 把所有任务放进"待排"。已完成的任务:开始 = 结束 = -1,不占用容量。
2. 重复:
   a. 找出"可排"任务 = 它的所有依赖都已排好。
   b. 在可排任务里,先排优先级高的(H→M→L),同优先级按编号。
   c. 对这个任务:
        最早开始日 = max(依赖任务的结束日) + 1,至少为第 0 天
        对它的每位分配(未拒绝、未完成):
            从最早开始日往后逐天,每天取 min(当天剩余容量, 还没做完的小时),
            直到该成员的小时做完 → 记下结束日
        任务结束日 = 各成员结束日的最大值
        任务开始日 = 各成员第一次有工作的那天的最小值
   d. 该成员当天容量被用掉的部分要扣除,下一个任务才不会重复使用。
3. 找不到可排任务但还有待排 → 依赖有循环,报错。
4. 任务没有任何有效分配(全被拒绝) → 标为"阻塞",它与它的后续任务结束日视为无限大。
5. 某成员在 200 天内也做不完 → 结束日视为无限大。
```

**每个任务的多人并行**:同一任务的各位成员从同一天开始各做各的,任务在最后一位做完时结束。

### 3.4 风险状态(不要手动设置,一律计算)

```
截止日(第几天) = deadline 日期 − 今天
预测完成日   = 所有未完成任务的结束日的最大值

状态:
  没有未完成任务              → Complete
  截止日 < 0                  → Overdue
  预测完成日 > 截止日          → At Risk     (延误天数 = 预测完成日 − 截止日)
  否则                        → On Track
```

- **成员超载** = 该成员剩余工作小时 > 他到截止日的可用小时总和。
- 注意:**"没有人超载"也可能 At Risk**。原因是依赖链太长或某个人的时间集中在某几天(我们的示范项目就是这种情况)。所以风险提示要同时显示"依赖链"和"个人容量"两种因素。
- **关键路径**:从结束日最晚的任务开始,往前找"结束日最晚的未完成依赖",连成一条链。Defender 的"Main risk"可以用它说明。
- 每次下面任何一件事发生,都要**重新排程并重新算风险**:任务状态改变、剩余小时改变、分配改变、优先级改变、依赖改变、成员可用时间改变、deadline 改变、任务被拒绝、Rescue 被套用。

### 3.5 任务状态

任务状态不是手动存的,由各分配的状态推导:

```
被强制标记完成(leader override)           → Done
没有有效分配                              → To Do(并标"需要重新分配")
所有有效分配都 Done                        → Done
有任何有效分配不是 To Do(进行中或已完成)   → In Progress
否则                                      → To Do
```

- 多人任务,**必须所有人都做完才算 Done**,除非 leader 明确 override(要弹确认窗,并说明排程会怎么变)。
- 被拒绝的分配不参与计算。

### 3.6 进度计算

```
成员进度 %     = (他所有任务的"已分配小时 − 剩余小时"之和) ÷ 已分配小时之和
成员任务数      = 完成任务数 / 他负责的任务数
整体进度       = 所有成员已做小时之和 ÷ 所有已分配小时之和
整体完成任务数  = 同一任务的所有分配都 Done 才算该任务完成(同一任务不要重复计数)
成员状态标签    = 在关键路径上 → "On critical path";已有进度 → "On track";没有进度 → "Not started"
```

### 3.7 优先级

- 由 AI 在 Plan 生成时提出,依据(按重要性):rubric 分数占比与必修要求 → 有多少任务依赖它 → 离到期日有多近。
- `priority_reason` 要保存真实数字,任务详情的 "Why this priority" 直接显示,例如"占 30 分里的 4 分、3 个任务依赖它、2 天后到期"。
- Leader 可以手动改优先级,改了要重新排程(高优先级先分配容量),并弹确认窗显示新的预测完成日。
- Rubric 只用来排优先级,**不需要单独的 rubric 页面**。

### 3.8 分配与匹配

给任务选人时的评分(分数越高越适合):

```
技能匹配   = 该成员对任务所需技能的最高强项等级(0 = 没有、1/2/3)
弱项惩罚   = 任务所需技能在他的弱项里 → 大幅扣分(不是绝对禁止)
空档      = 他到截止日的可用小时 − 已有剩余工作
```

- 先看技能匹配,再看空档,弱项扣分后排最后。
- 空档不足就不能分配(除非其他人也都不行,这时要标示)。
- 大任务可拆给多人,每人的小时数加起来要等于任务总估时。
- 所有人都不适合 → 回报"没有合适成员",让 leader 决定(增加成员、放宽要求)。

### 3.9 AI Deadline Defender

**触发**:排程结果是 At Risk 或 Overdue 才显示风险页;On Track 显示"没有风险"。**必须先选原因,leader 才能按 Run**。不能自动开始。只有 leader 能执行。

**原因的作用**:原因要传给 AI,并影响策略。例如:
- 成员不能做 → 先把这位成员的剩余工作全部处理掉;
- 成员超载 → 优先转移他的低优先级、尚未开始的工作;
- Deadline 提前 → 容量按新的截止日重新计算;
- 任务比预期慢 → 把相关任务的剩余小时调大再排程。

**变更要不要批准**(程序强制):

```
需要 leader 批准 = 任务被锁定  或  成员已接受该分配  或  该分配已在进行中
可自动套用       = 以上都不是(没开始、没接受、没锁定)
任何情况都不能改   = 已完成的任务
```

**验证循环(最多 3 轮,每轮都从原计划开始)**:

```
第 1 轮  只动"可自动套用"的工作 → 重排 → 预测完成日 ≤ 截止日?
第 2 轮  允许动需要批准的工作,并允许放宽依赖(例如让汇总任务不必等所有图表完成) → 重排 → 验证
第 3 轮  再加入"降低范围"(只能动 Low 优先级任务,绝不动 High)→ 重排 → 验证
每轮内部:最多 8 步,每步试所有候选(转移一半或全部小时给有该技能、有空档的人),
         选"预测完成日最早"的那个;没有改善就停止。
```

**结果判定**(不是由 AI 说了算):

```
还有"需要批准"的变更未决定            → Approval Required
全部决定后,重排的预测完成日 ≤ 截止日   → Rescue Validated
全部决定后仍然晚                      → Risk Unresolved(说明剩余限制,并提供降低范围的选项,需批准)
```

- Leader 拒绝某提案 → 重新计算结果,可能从 Validated 变成 Unresolved。
- **Before vs After** 的数字全部用排程程序算:预测完成日、风险状态、每人工作量、剩余风险(例如"没有缓冲时间")。
- **套用**:一次完成。步骤:用最新资料重新验证 → 套用已批准与可自动套用的变更 → 重新排程 → 更新风险状态 → 写入变更记录。若期间别人改过任务,验证失败要提示重新跑。
- "Discard"则不改任何资料。

### 3.10 成员接受与拒绝

- 新分配默认 `pending`。成员可 Accept 或 Reject。
- **Reject 必须选原因**:时间不够、技能不足、工作量太多、其他(可补充说明)。
- Reject 后:该分配不再算入排程,任务可能变成"阻塞",并触发重新分配建议(用第 3.8 节的评分,排除拒绝者)。
- 找不到人 → 回报"没有合适成员"。
- Accept 后,这份工作在 Defender 里属于"需批准才能动"。

### 3.11 Leader 编辑任务

- 可编辑:标题、说明、优先级、目标日期、每位成员的已分配与剩余小时、增减成员、是否锁定。
- 改动会影响排程的(优先级、小时、成员)→ 先算新旧预测完成日,在确认窗里显示"从 X 变成 Y",确认后才保存。
- 修改后受影响的成员要重新 Accept(预设:小时变多时才需要)。
- 只有 leader 能做这些。

### 3.12 边界情况清单

| 情况 | 应该怎么处理 |
|---|---|
| 成员被移除,但还有任务 | 他的未完成分配变成"无人负责",任务标"需要重新分配",并触发匹配建议 |
| 成员一周总可用小时 = 0 | 不能保存;已存在的则警告,不分配任务 |
| 总剩余工时 > 团队总可用小时 | 直接标示"即使重新分配也赶不上",Defender 优先建议降低范围 |
| 依赖有循环 | 排程报错,要求 AI 重新给依赖(Plan 生成阶段就要验证) |
| 任务被全部拒绝 | 标"阻塞",后续任务也阻塞,预测完成日为"无法预测" |
| Deadline 已过 | 状态 Overdue,Defender 说明无法在期限内完成,只能提供"尽快完成"的排法 |
| 没有 rubric | 如实告知,优先级只用依赖与截止时间判断 |
| AI 调用失败或超时 | 保留用户资料,显示失败状态并提供重试 |
| 排程期间资料被别人改过 | 套用前重新验证 |
| 时区 | 所有时间带时区储存与比较 |
